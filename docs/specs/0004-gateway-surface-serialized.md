# FS-0004: The whole gateway surface, serialized and governed

> Status: work-order · SPECIFICATION.md: services/api-gateway/SPECIFICATION.md "## Contract" + client/SPECIFICATION.md "## API integration" → this FS · Related ADRs: docs/adr/0006-batch-retrofit-of-the-remaining-surface.md (governing), docs/adr/0002-contract-planes-code-first-openapi.md, docs/adr/0003-serialized-transport-types.md, docs/adr/0004-error-representation-rfc9457.md, docs/adr/0005-request-validation-and-contract-design.md

## Summary

The api-gateway exposes 34 HTTP operations. Two of them — the profile pair from FS-0002 — are
serialized, typed, and described by a generated OpenAPI 3.1 document. The other 32 are legacy
gin handlers returning a `{statusCode, message, result}` envelope, described only by a
hand-written swaggo OpenAPI 2.0 document.

This feature serializes all 32, moves the frontend onto a generated client, and closes three
gaps that currently let the gates pass without doing anything. Nothing a user can do changes.
What changes is that the entire HTTP surface stops being implicitly defined by handler code and
starts being governed by a contract derived from it.

The swaggo document was removed **first**, ahead of every slice (ADR-0006 §5 as amended), so
the campaign runs against a single description throughout. Until a group lands, its operations
are reachable but undocumented — a deliberate, stated trade, not a defect.

This is the discharge of ADR-0002's serialize-on-touch clause, decided in ADR-0006.

## Requirements

### Serialization

1. Every operation in `§API surface` is served by a huma-registered typed handler mounted on
   the existing gin engine. **No path changes, no method changes.**
2. Public operations (`signup`, `signin`) are registered without the auth middleware and
   without a `Security` block. Every other operation runs the existing
   `auth.AuthMiddleware` and declares `Security: bearerAuth`.
3. Operations are registered through **one** registration path, called by both the router and
   `cmd/openapi`. Registration must run with no infrastructure — no network, no DB — so the
   document can be generated in CI.
4. Response bodies are **bare resources**. The `{statusCode, message, result}` envelope is
   removed (ADR-0003, ADR-0006 §3). This is a deliberate break; see R14.
5. Each group declares dedicated transport types. Downstream protobuf messages and internal
   `models.*` types must not appear in the generated schema, directly or nested (ADR-0003 §3).
6. Transport types are **transcribed from what ships today**, field name for field name,
   including `omitempty`. Existing inconsistencies are preserved, not fixed — `insights` takes
   `plan_id` while `notes` takes `isRead`, and both stay as they are. Renaming is a later
   feature's job (ADR-0006 §2).
7. Where two groups need the same type name, it is declared once in a shared package. Huma
   keys schemas by **type name**, so a duplicate declaration panics the generator rather than
   producing a wrong document.
8. Every operation declares `Summary`, `Description`, and its full `Errors` list. Spectral
   rejects an operation missing any of them.

### Errors

9. Failures on serialized operations are RFC 9457 `application/problem+json` carrying a stable
   `code`, via the existing `apierr.Problem` (ADR-0004). No new error boundary is created —
   the serialized surface adds a second serialization of the existing one.
10. `errors[]` is always present, empty when there is no field-level detail.
11. Every error a handler returns passes through the problem adapter. A raw error returned
    from a handler is read by huma for its status and bypasses the mapping.
12. Shape violations are **422** `VALIDATION_FAILED`, produced at the boundary by huma from
    the type. Domain rules stay in the owning service and keep their current status and code.
    The gateway never restates a downstream rule (ADR-0005).
13. `apierr.StatusFor` gains a `codes.Unavailable` case. It is currently absent, so a
    downstream outage maps to 500 instead of 503.

### Verification of the deliberate break

14. Envelope removal is invisible to the breaking-change ratchet — these operations were not
    in the previous document, so there is no diff to detect. Each group's slice records a
    **before/after probe against a running gateway** as its evidence: the legacy response and
    the serialized response, side by side, showing the envelope gone and the payload identical.
15. Each group carries a round-trip test that marshals a **populated** downstream message,
    converts it to the transport mirror, marshals that, and asserts the two JSON documents are
    equal. Populated matters: every field is `omitempty`, so zero-valued fixtures compare `{}`
    to `{}` and prove nothing.

### Frontend

16. `client/src/api/generated/` carries a generated `openapi-fetch` client, regenerated by
    `make client` and never hand-edited.
17. All calls to serialized endpoints go through that client. The three remaining raw call
    sites — `services/api.ts`, `components/Todo.tsx`, `app/plan/[planId]/page.tsx` — are cut
    over.
18. A lint rule bans bare `fetch` outside the single client module, and the rule is proven to
    **reject a fixture** — a lint rule that matches nothing passes silently.
19. Each group's FE cutover lands in the same slice as that group's envelope removal, so no
    consumer observes a half-migrated group.

### Retirement and gates

20. **Done up front, ahead of every slice** (ADR-0006 §5 as amended): the `/swagger` mount, the
    `//@` annotations, `services/api-gateway/docs/`, `make gen`, the `lint`/`docs` targets, the
    orphaned gateway-local Spectral ruleset, and the `swaggo` + `gin-swagger` dependencies are
    removed. The generated OpenAPI 3.1 document is the only description of the HTTP surface
    from the start of this feature, not the end.

    The consequence is deliberate and must not be treated as a defect during the campaign:
    until a group is serialized, its operations are **reachable but undocumented**. The
    document's `info.description` says so explicitly, so it understates its coverage rather
    than misrepresenting it.
21. `--fail-on ERR` becomes `--fail-on WARN` in the ratchet target. `ERR` alone does not catch
    a field rename.
22. A `gates-selftest` target runs the existing `contract-fixtures/` and is wired into
    `make gates`. It must assert on **exit status**, not on grepping output for "error", and
    its file globs must be verified to match real filenames — a selftest that globs nothing
    passes vacuously.
23. A `check-contract-auth` gate asserts *runs auth middleware ⇒ declares security*, read from
    **Go source**. It must not infer "needs auth" from a documented 401: `signin` answers 401
    for bad credentials while requiring no token.

## User Stories

1. As a frontend developer, I want every gateway endpoint in one browsable document, so that I can learn the API without reading Go handlers.
2. As a frontend developer, I want generated TypeScript types for every endpoint, so that a contract change breaks my build instead of a user's session.
3. As a frontend developer, I want to see which endpoints need a token, so that I know what to send before I call them.
4. As a frontend developer, I want to exercise a protected endpoint from the docs page, so that I can check a response shape without writing code.
5. As a frontend developer, I want one place that describes the API, so that I never have to work out which of two documents is current.
6. As a backend developer, I want the contract derived from my handler signatures, so that I cannot forget to update it.
7. As a backend developer, I want a renamed field to fail CI, so that I find out before a consumer does.
8. As a backend developer, I want to add an endpoint without also writing an annotation block, so that there is no second description to keep in sync.
9. As a backend developer, I want the gates to be proven against known-bad inputs, so that a green check means they ran.
10. As a backend developer, I want a downstream outage to surface as 503, so that a caller can distinguish "try again" from "this is broken".
11. As a new team member, I want the docs page to show the whole API, so that my first impression is not that the system has two endpoints.
12. As a reviewer, I want each group's envelope removal shown as a before/after probe, so that I can check a break the ratchet structurally cannot see.
13. As a reviewer, I want transport types transcribed rather than improved, so that I can review one kind of change at a time.
14. As a consumer of the API, I want errors in one shape with a stable code, so that I can branch on the code and display the detail.
15. As a consumer of the API, I want `errors[]` always present, so that I never null-check before iterating.
16. As an operator, I want the OpenAPI document generatable without a database or network, so that CI can build it.
17. As a maintainer, I want the swaggo dependency gone, so that nobody can hand-edit the API description.
18. As a maintainer, I want the retrofit tax removed from unrelated features, so that touching one checklist endpoint costs what that change costs.
19. As a maintainer, I want a lint fence on raw fetch, so that the generated client does not erode back into hand-written calls.
20. As a maintainer, I want the lint fence proven against a fixture, so that I know it rejects something.
21. As a maintainer, I want shared transport type names declared once, so that the generator does not panic as groups are added.
22. As an API consumer, I want unknown request members rejected, so that a typo fails loudly rather than being silently ignored.
23. As a security reviewer, I want every middleware-protected operation to declare its security scheme, so that the document cannot understate what is protected.
24. As a security reviewer, I want that property enforced by a gate, so that it stays true as operations are added.

## Acceptance Criteria

- [ ] All 32 operations in `§API surface` are registered as typed huma operations and appear in the generated `openapi.yaml`.
- [ ] `openapi.yaml` regenerates byte-identically from a clean checkout (`make openapi-diff` green).
- [ ] `cmd/openapi` generates the document with no database and no network.
- [ ] No `models.*` type and no protobuf message appears anywhere in `components.schemas`.
- [ ] Every serialized success response is a bare resource — no `statusCode`/`message`/`result` wrapper anywhere in the document.
- [ ] Each group has a round-trip test over a **populated** fixture asserting JSON equality between the downstream message and its transport mirror.
- [ ] Each group's slice records a before/after probe showing the envelope removed and the payload otherwise unchanged.
- [ ] Every operation declares `Summary`, `Description`, and its `Errors` list; `make lint-contract` is green.
- [ ] Every operation running `auth.AuthMiddleware` declares `Security`; `signup` and `signin` declare none.
- [ ] `check-contract-auth` passes, and has been observed failing when one `Security` declaration is removed.
- [ ] `gates-selftest` passes, and each fixture has been observed being **rejected** by the gate it targets.
- [ ] The ratchet runs with `--fail-on WARN` and produces no false positives on an unchanged document.
- [ ] A downstream `codes.Unavailable` maps to 503, proven by a test.
- [ ] `client/src/api/generated/` contains a generated client; `make client` reproduces it byte-identically.
- [ ] No raw `fetch` or `axios` call to a gateway path remains outside the client module.
- [ ] The lint fence rejects a fixture file and accepts the tree, proven by a recorded run.
- [x] `/swagger` is gone, `docs/docs.go` is deleted, `make gen` is removed, and `swaggo`/`gin-swagger` are absent from `go.mod`. *(done up front — build, vet, and the full suite green; `make gates` green)*
- [ ] `/api/docs` renders all 34 operations with padlocks on the protected ones.
- [ ] Full Go test suite and the client typecheck are green.

## Edge States

- **Downstream service unavailable** — 503 `UNAVAILABLE` with `errors: []` (R13). Currently 500; this is the one status change in the feature and is a fix, not a transcription.
- **Unknown member in a request body** — 422 `VALIDATION_FAILED` at the boundary, never forwarded downstream (ADR-0005, `strict`).
- **Malformed JSON body** — 400. Distinct from a shape violation on well-formed JSON, which is 422. This distinction was confirmed empirically in barrowspire; do not assume all body problems are 422.
- **Empty list result** — `[]`, never `null`. Proto slices marshal to `null` when nil and a consumer iterating `null` breaks.
- **Missing or malformed bearer token** — 401 `UNAUTHENTICATED` from the middleware, before the handler runs.
- **Unparseable UUID path param** — current behavior maps it through `ErrUUIDCouldNotBeParsed`; transcribe the resulting status rather than assuming 400 or 422.
- **`GET /analytics/user/:userId` on the stub path** — the handler returns 501 today. The operation is published with 501 in its `Errors` list; the success shape is declared from `internal/useranalytics/model.go` and is **unproven until the data path lands**. Say so in the slice, do not claim it verified.
- **Insights with a missing `plan_id`** — the query param is parsed as a UUID; an absent value fails the same way a malformed one does. Transcribe as-is.
- **Notes `tags` supplied repeatedly** — `QueryArray` is used, so `?tags=a&tags=b` is a two-element filter. The typed param must be a slice or this silently degrades to the last value.
- **Concurrent regeneration** — `openapi.yaml` and the generated client are committed together with their handler change; a diff containing one without the others fails `openapi-diff`.

## Out of Scope

- **Plane 2 (gRPC) governance.** `buf lint` / `buf breaking` remain unwired; still an acknowledged gap.
- **Any downstream service's API.** This feature governs the edge only.
- **Redesigning any shape.** Field names, param casing, timestamp representation, and the unbounded `listUsers` are transcribed as-is (ADR-0006 §2). Each is a candidate for its own later feature.
- **Completing the analytics data path.** The stub is published, not fixed.
- **Pagination anywhere it does not already exist.**
- **The legacy prose sections of `services/api-gateway/SPECIFICATION.md`.** Their thin-format migration is a separate hygiene pass.
- **Auth-service's own validation rules.** The gateway never restates a downstream rule.
