# ADR-0002 — Contract layer: two planes, design-first process with code-first generation

Status: accepted
Date: 2026-08-04
Scope: root — governs api-gateway, client, and the `common/api/proto` plane
Realized by: no single FS — adopted per **serialize-on-touch** (slice ⓪ of the first
feature that touches each endpoint's surface)
Amended by: **ADR-0004** — the error clause below (RFC-7807, stock error model) is replaced
by RFC 9457 problem+json with `code` + `errors[]` extensions. Every other decision here
stands. The body is left unedited on purpose: ADRs are immutable, so read the text below as
the record of what was decided on 2026-08-04, and ADR-0004 as what holds now.

## Context

Fireplace has two boundaries where a contract exists whether or not we govern it, and
today they are governed unevenly.

**Plane 1 — client ↔ api-gateway (HTTP).** The gateway is the only HTTP surface. Its
spec is produced code-first by `swaggo/swag` from `@`-annotated handlers
(`make gen` → `docs/swagger.{json,yaml}` + `docs/docs.go`), served at
`/swagger/index.html` via `gin-swagger`, and linted with Spectral. The governing
principle is already right — *code is the source of truth, the spec is a generated
description of shape, never hand-maintained* (`services/api-gateway/docs/api-conventions.md`).
The **mechanism** is what fails it: annotations are comments. They are not typechecked,
nothing forces them to match the handler they sit above, and they drift silently. The
output is also OpenAPI **2.0**, which the modern TypeScript client generators treat as a
second-class input. On the consumer side there is no generated client at all — the
frontend hand-writes fetch calls (`client/src/services/api.ts`, `notesService.ts`), so a
gateway change breaks the client at runtime rather than at `tsc`.

**Plane 2 — service ↔ service (gRPC).** `common/api/proto` already *is* the contract for
the seven downstream services, with committed `.pb.go`. It has no lint and no
breaking-change gate; a field can be renumbered and nothing objects until a service
misbehaves in an environment.

The deeper force is a process one, not a tooling one. Two things get conflated under the
word "the contract": its **design** (what resources exist, what an operation *means*,
what errors are possible — human judgment, expensive to get wrong) and its
**serialization** (the YAML — mechanical, derivable). Handing both to an agent inverts
design-precedes-implementation at the single most expensive boundary in the system.
Hand-authoring both produces two artifacts that drift.

### Alternatives considered and rejected

- **Spec-first** (hand-authored YAML → generated server stubs). Two authored artifacts
  that drift against each other, and YAML authorship is precisely the mechanical work we
  delegate. Correct only when the contract **is** the product — a public, third-party API.
  Ours is a one-brain internal boundary.
- **Pure code-first with no designed table.** The agent authors the contract and review
  discovers it after the fact. This is the inversion described above; it is the status quo
  with better tooling, not a fix.
- **Annotation-based generation (swaggo — the current state).** Comments enforce nothing
  and drift from the code they describe; OpenAPI 2.0 output constrains the client
  toolchain.
- **Big-bang migration of every gateway endpoint.** Spends sessions protecting endpoints
  that may never change again. Adoption should be triggered by the work, not scheduled
  ahead of it.

## Decision

**Design-first process, code-first generation** — the two halves are separated and each
is given to whoever should own it.

1. **Plane 1 design lives in the feature spec.** The contract's DESIGN is the
   `§API surface` table in each feature's `FS-NNNN` — prose and a table, human-ratified at
   promotion like every other spec section. It pins **shape** (op, method + path, params,
   request, response, errors); semantics stay in Requirements. It is **never** YAML and
   never Go types.

2. **Plane 1 serialization is generated, committed, and never hand-edited.**
   `openapi.yaml` is generated by **Huma v2** from the gateway's *typed handler
   signatures* — types, not comments, so it cannot drift from the code. It is committed:
   the YAML diff **is** the contract review surface on a PR. CI regenerates and **fails on
   any diff** between the committed and derived spec.

3. **Plane 1 gates.** `oasdiff` against the committed spec detects breaking changes — an
   `ERR` blocks merge; a deliberate break goes through an `.oasdiff.yaml` allowlist, which
   makes the break an explicit, reviewable act. `Spectral` enforces contract depth:
   descriptions, examples, and error schemas required.

4. **The client consumes only the generated TypeScript client.** Generated with
   `openapi-typescript` + `openapi-fetch` into `client/src/api/generated`. Hand-written
   fetch against a **serialized** gateway endpoint is a **HIGH** code-review finding.

5. **Plane 2 is governed by buf.** `common/api/proto` is the contract as-is; governance
   is `buf lint` + `buf breaking` in CI, mapping to the same HIGH/MED/LOW severities into
   `.audit/` as plane 1. Events and WebSocket payloads ride this same plane.

6. **Adoption is serialize-on-touch, never big-bang.** An existing gateway endpoint is
   wrapped into Huma — behavior-preserving, into the YAML — as **slice ⓪** of the first
   feature or refactor that touches its surface. **No handler rewrite may precede its
   endpoints' serialization**: the contract is established at signature time, before the
   behavior changes underneath it.

7. **Grandfather clause.** The generated-client-only rule (4) binds **serialized**
   endpoints. Legacy endpoints may keep their existing fetch calls until touched, at which
   point the frontend call migrates **within the same feature** — the FE and BE halves of
   one endpoint never straddle two features.

8. **This supersedes the swaggo / gin-swagger pipeline.** No new `@`-annotations are
   written. `make gen` and the generated `docs/` package are removed when the last legacy
   endpoint serializes; until then the OpenAPI 2.0 Swagger UI continues to serve **legacy
   endpoints only**. (No prior ADR is superseded — swaggo was an established practice, not
   a recorded decision.)

**Toolchain pinned:** `huma v2`, `oasdiff`, `spectral`, `openapi-typescript` +
`openapi-fetch`, `buf`.

## Consequences

**Accepted / positive:**

- The expensive half of the contract (design) is decided by a human in the FS *before*
  implementation; the mechanical half (serialization) is derived and cannot drift.
- Generation from **typed signatures** rather than comments removes the drift class
  entirely — the spec is wrong only if the code is wrong.
- The FE breaks at `tsc`, not at runtime: a gateway change that invalidates a client call
  fails the build.
- Breaking changes become a deliberate, allowlisted act instead of an accident discovered
  downstream.
- Plane 2 gains the same gate shape as plane 1 — one severity vocabulary, one `.audit/`
  destination, isomorphic review habits across both boundaries.
- Migration cost is paid only where work is actually happening.

**Costs / follow-ups:**

- **Huma adoption at the gateway** is a per-endpoint migration cost, paid incrementally.
- **One error-mapping adapter** is required, translating downstream gRPC statuses into
  RFC-7807 problem responses.
- **The error BODY format changes to `problem+json` for wrapped endpoints** — a known,
  deliberate break. Any client code reading the current error shape must migrate with its
  endpoint.
- **Generated artifacts are committed**, so PR diffs get larger. Accepted: that diff is
  exactly what makes the contract reviewable.
- **A transitional period** where serialized and legacy endpoints coexist, with two
  documentation surfaces live (`openapi.yaml` for serialized, the OpenAPI 2.0 Swagger UI
  for legacy). Tracked with a thin-spec line — *Legacy surface serialized → FS-none* —
  so the remaining migration is visible in the capability index rather than in memory.
- **`services/api-gateway/docs/api-conventions.md` must be rewritten or retired** with the
  pipeline it documents. Its governing principle survives; its swaggo mechanism does not.
- `client/src/api/generated` does not exist yet; it is created by the first serialized
  endpoint's slice, alongside the client-generation step in CI.
